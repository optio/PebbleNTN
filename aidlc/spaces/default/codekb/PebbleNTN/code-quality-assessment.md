### Vela Maps findings (intent 261030-vela-maps, focused scan at c7b6ba0)

The full fact list with line numbers is the intent's developer scan handoff (`inception/reverse-engineering/developer-scan.md`); the points that shape the change:

1. **Registration.** Catalog entry, `<queries>` line (`validate_catalog.py` fails without it), `rules/bundled/vela-maps/en.json` with `packageNames: ["app.vela"]` in every rule (`NavigationAppCatalogTest` requires the folder name to be the `appId` and `hasOfficialRules: true`), `rules/fixtures/vela-maps.json`, a new `VelaMapsRulesRegressionTest`, the workbench regression tuple, the catalog lock-table row, `test_validate_catalog.py` 27 to 28, and `SetupProgressTest.kt:30` (`vela-maps` joins the apps with directions, last alphabetically). README, the fastlane full description and `rules/fixtures/README.md` list apps by hand (README and `requirements/REQ-RULES.md` are MANIFEST-protected). No main-source Kotlin change: the UI, enablement and rule loading are catalog- and folder-driven.
2. **Google Play.** `playListed: false` without `rulesFrom` makes `forGooglePlay()` drop the entry and its package, so a Play install never allowlists `app.vela` (the first such entry). `NavigationAppCatalogTest.kt:283` still counts 27, and its "nothing is lost" comment no longer holds. The catalog schema's `playListed` description only covers the `rulesFrom` case.
3. **The issue's rules validate.** Every operator, extractor and maneuver token exists; Vela's source confirms the title (`In %1$s · %2$s`, `Arrived`, `Navigating`, or the bare instruction at distance 0) and the text (`<duration> · <distance> · Arrive <time>` plus optional stop and faster-route parts). Distances are `ft`, `mi`, `m`, `km` with a `.` decimal, which `DistanceParser` reads.
4. **Rule problems.** (a) Every maneuver rule requires `^In`, so a bare-instruction title gives UNKNOWN; (b) a Valhalla-style "Take the I 35 South exit" misses the exit rule and matches the roundabout's `take the .+ exit` (same priority 150, exit first by id); (c) exits and ramps always give SLIGHT_RIGHT, U-turns always UTURN_LEFT; (d) the turn rules (160) outrank the roundabout (150) for "At the roundabout, turn right"; (e) no ARRIVE for "Your destination is …" or "Arrive at …" with or without a distance; (f) "Bear left/right" is missing; (g) `head|continue|merge` gives STRAIGHT, as Google Maps' merge rules do; (h) the two text extractors are repeated in 12 rules. All of this is from reading, not from captures.
5. **ETA.** `secondaryText` is only the clock ("12:45", "12:45 PM"), the bundled convention (Google Maps, CoMaps); no bundled rule sets `etaEpochSeconds`. With a stop ahead the clock is the stop's.
6. **Evidence.** Every fixture would be synthetic. The instruction wording depends on Vela's router and app version, and Vela localizes, so English rules match only English devices. The reporter offered a diagnostics export on #120.
7. **Route capture.** A `VelaMaps(App)` driver (`app_id` `vela-maps`, `package` `app.vela`, a `ReleaseAsset` on `api.github.com/repos/PimpinPumpkin/Vela/releases` with an anchored `vela-maps-x86_64.apk` pattern that skips the `canary` pre-release), an `APPS` entry, a plan (English first; every route is European, so an imperial en-US run needs a new route), README rows, and a `matched: false` fixture for the `Navigating` card (its text carries a clock, so the harness would count it as missing). Unverified until run on the Windows emulator: whether the `google.navigation:` intent starts guidance or opens a preview (button ids, first-run dialogs), whether `mode` is honoured, and whether online routing works in the emulator. `is_instruction` accepts Vela's cards through the clock in the text; UNKNOWN matches (the generic and bare rules) are listed as fallbacks, which suits discovery.

### MicroG icon fallback findings (intent 261028-microg-icon-fallback, focused scan at 2fa2aa5; shipped in v0.0.79, not rescanned)

The full fact list with line numbers is the intent's developer scan handoff (`inception/reverse-engineering/developer-scan-PebbleNTN.md`); the points that shape the change:

1. **Where.** `AppIconReferences.render` (`notification/icon/AppIconReferences.kt:35-43`) opens `createPackageContext(posting)` and calls `getIdentifier(name, "drawable", posting)`; `id == 0` skips the drawable (:39). The retry belongs there, in the same context, with only the `defPackage` argument changed.
2. **No root in the model.** `RuleFamilies` (`catalog/NavigationAppCatalog.kt:136-160`) stores `Map<String, Set<String>>`; `ruleFamilies()` (:59-61) groups by `rulesAppId` into a `linkedSetOf` in catalog order. Root-first holds today only because `google-maps` precedes `microg-maps` in the catalog; nothing enforces it. Record the root explicitly: the `rulesFrom` target's first package off Play, the merged entry's first package on Play (`forGooglePlay`, :71-82). Both give `com.google.android.apps.maps`.
3. **Wiring.** `RuleDrivenLargeIconRecognizer` (`LargeIconRecognizer.kt:24-37`) already receives `families` from `AppContainer.kt:137-138` but builds the default `AppIconReferences(context)`; the root has to reach `render` either as a `references(...)` argument or through the `AppIconReferences` constructor.
4. **Cache.** Keyed by posting package, version code, density and candidates; empty results are cached; a miss evicts the package's older keys (`AppIconReferences.kt:20-31`). A retry inside `render` needs no cache change because the root is fixed per process.
5. **Scope of the retry.** Only `microg-maps` uses `rulesFrom`, but OsmAnd, Organic Maps and CoMaps are multi-package families too, and CoMaps and Organic Maps map icons. A retry keyed on "family root differs" would also run for their variants on a miss; keyed on `rulesFrom` (or Play merge) it stays MicroG-only. `RuleFamilies.NONE` must mean no retry.
6. **Unsafe variants.** Do not open the root app's own context (that would read real Google Maps drawables and depend on a second install), and do not retry with packages outside the catalog (for example `android`).
7. **Tests.** Nothing fakes `createPackageContext`/`getIdentifier`. A pure "resource packages to try" function and an injectable `(name, defPackage) -> Int` lookup make the fallback testable without a device.
8. **Unverified premise.** That the patch kept the Google resource-table name is a hypothesis; on a device the debug-history `iconMatch` shows `no match: no references` when no drawable resolves (`IconMatcher.kt:84`).

### Version-compare update findings (intent 261022-version-compare-update, focused scan at 1ad9ec8)

Status at c50710e (v0.0.73): findings 1-5 were addressed by the merged work. The phone records the watch's key 11 from a genuine READY (finding 1; its claim that the Core Devices companion does not forward the real READY was disproved on a real phone with v0.0.74), each device derives its own effective update (2, 4), `AppVersions.parseStrict` / `isNewerStrict` and the watch `version_compare.c` reject unparsable versions (3), and `InstallSources` drives a per-source card (5). Finding 6 was not re-checked. The original findings are kept below for history.

1. **The phone has no reliable source for the watchapp version.** The watch sends key 11 only in its real `WATCH_READY`, once from `init()` (main.c:997-1007, 1197). `ProtocolCodec.decodeInbound` drops it, and `ReducerEvent.WatchReady` has no version field. The Core Devices companion does not forward the real READY (NavigationController.kt:138-148). The synthetic READYs (`scheduleAutonomousReady`, `WatchListenerService.appOpenedReadyMessage`) have no key 11. PebbleKit 2 exposes firmware version only. The phone half of the comparison is therefore best-effort; the watch half is reliable, because the phone sends key 11 on every message.
2. **The watch's update record is overwritten by every message.** `update_record` clears `s_latest_phone_version` whenever bit 4 is clear (update_notice.c:110-117). A watch-side comparison result needs its own derived "effective latest" that feeds the notice, the idle text and the glance.
3. **`AppVersions` does not reject unparsable versions.** Non-numeric components become 0 and suffixes are dropped (AppVersions.kt:26-35), so "garbage" compares as 0. The intent requires ignoring unparsable versions, which needs a strict parse. The watch has no comparator, so it needs a new pure C unit with its own `test_<unit>.c`.
4. **There are two "update available" sources on the phone.** The GitHub `latestVersion` drives the card text, `latestPhoneUpdate` and persistence. A watch-reported version needs a defined precedence (for example, the higher of the parsable versions) so the card version and key 14 agree.
5. **There is no install-source detection.** The card has a single hard-coded GitHub URL and GitHub-specific body text (strings.xml:40-41, 58; MainActivity.kt:157). The installer-package mapping (F-Droid clients, Obtainium, unknown or browser to GitHub) is not in code.

### Settings sync findings (intent 261025-settings-sync, focused scan at 4779760)

Status at 6dec020 (v0.0.77): shipped (#102, REQ-WATCH-025 and REQ-ANDROID-021). The findings below are kept as they were written before the work.


Issue #102 (groomed 2026-10-24/25) against the code at 4779760 (v0.0.76):

1. **23 settings, one owner.** The synced set is persist keys 1-15 (`theme.c`) plus 19 (Touch) and 20-26 (shortcut slots), which matches the issue's "about 23". Key 27 (last vibration pattern) is internal and is updated by `settings_set_vibe_pattern` itself; keys 16-18 are version records. Ranges and defaults: [api-documentation.md](api-documentation.md). The next free persist key, for a stored revision, is **28**. The protocol has keys 0-14 at version 1.2; keys 15 and up, events 4-9 and 13 and up, and flag bits 5-31 are free.
2. **WATCH_READY is sent once per launch, not "on every connect".** `send_ready()` runs only at the end of `init()` (main.c:1360); `app_connection_handler` only restarts the watchdog. A watch edit made while the phone is away, during a session, would reach the phone at the next app launch unless the watch also sends on reconnect or on its next outbound chance. The watch never sends WATCH_REQUEST_STATE.
3. **The phone fakes READY with its own protocol version.** `scheduleAutonomousReady` and `WatchListenerService.appOpenedReadyMessage` build WATCH_READY with the phone's `Protocol.MAJOR`/`MINOR`. The issue's rule "show the settings screen once the watch reports the new protocol minor" would be satisfied by these fakes. Support must be detected from the genuine READY's settings or revision keys, the way `ProtocolCodec.watchAppVersion` already distinguishes the real READY by key 11. The reducer reads only the major.
4. **Sending to a closed watchapp relaunches it.** `PebbleWatchTransport.send` relaunches the watchapp on `FailedDifferentAppOpen` while auto-launch is on (on by default). A phone edit sent at once while the watchapp is closed would open it on the wrist, against the launch policy in `spec/200-architecture/Pebble.md` (relaunch only for a pending state update, never while idle; REQ-WATCH-006). The offline queue therefore has to hold the edit until a READY, or use a send without the relaunch.
5. **No outbox handling on the watch.** No `app_message_register_outbox_sent/failed` handler exists, and `send_ready` drops the message when `app_message_outbox_begin` is busy. A watch-side SETTINGS send (after a menu edit, a Shortcut, or the confirmation reply) can collide with the READY or with another send and needs a pending flag and a retry.
6. **Where a watch edit can be caught.** All edits end in a `theme.c` setter: the menus (then `notify_change`), `shortcut_apply` (then `on_settings_changed`), and the Shortcuts door (`settings_set_shortcut`, `settings_set_touch_enabled`, without `notify_change`). Hooking `on_settings_changed` would miss the Shortcuts door. Applying a phone SETTINGS through the same setters must not count as a watch edit (no revision bump, no echo loop), except for the confirmation reply the issue asks for.
7. **Setters write flash even when nothing changed.** Every `settings_set_*` calls `persist_write_*` unconditionally. Applying a full 23-value SETTINGS through them writes 23 keys on every sync; apply only the values that differ.
8. **Validation is not quite "as `settings_load` does".** `settings_load` range-checks the int settings but reads the bools unchecked; `settings_set_accent` accepts all 16 accents on black-and-white watches (only the menu limits them to Black/White via `accent_for_row`), and the accent default differs by platform (Green 0 on colour, Black 14 on black-and-white); `shortcut_valid_action` keeps Next backlight colour (12) on non-RGB watches; the early-warning pattern range is 1-4, never Off. Incoming values need these platform rules, not just `< COUNT`.
9. **Open menus do not refresh.** `settings_window.c` has no public refresh call; menus re-read values only on redraw or `appear`. The Vibration door's row count depends on the early-warning distance and the Shortcuts door's on Touch, so a phone SETTINGS arriving while a menu is open needs a reload hook (or the menus popped) to avoid stale or out-of-range rows.
10. **The phone's `WatchSettings` overlap is smaller than it looks.** Only `autoLaunchOnSessionStart` is stored or shown (`WatchSettingsRepository`, key `watch_auto_launch`). `vibrateOnManeuverChange` (true), `activateBacklight` (false) and `exitToWatchfaceOnStop` (true) are fixed defaults with no UI, although REQ-ANDROID-009 lists vibration, backlight and return-to-watchface as settings. In effect the phone always asks for the maneuver-change pulse (bit 1), which the watch plays only while its own pattern is Off, and never asks for the backlight (bit 2). Dropping bit 1 in a clean-up would silence watches whose New instruction pattern is Off, the default.
11. **Platform and capabilities are not reported anywhere.** The watchapp never calls `watch_info_get_model()`; capabilities exist only as compile-time macros (`PBL_COLOR`, `PBL_ROUND`, `PBL_RGB_BACKLIGHT`, `PBL_PLATFORM_EMERY`) and the runtime `touch_service_is_enabled()`. PebbleKit 2 gives the phone the watch name and firmware only. aplite and diorite share 144x168 black-and-white; flint and gabbro are not build targets.
12. **Wire format and the mapper.** Integer tuples of any width arrive on the phone as `Int`; byte arrays are dropped. The watch reads integer tuples as `int32` without a type check, which is safe only because the phone always sends `Int32`. One int32 tuple per setting keeps both sides on paths that exist today; the 23 settings plus revision, platform and capabilities add about 286 bytes to READY (about 334 bytes in all).
13. **Protocol and spec edits are coupled.** `check_consistency.py` requires `protocolMajor`, `protocolMinor`, `keys` and `events` to equal `examples/protocol-definition.json`, which `MANIFEST.sha256.json` protects together with `spec/200-architecture/Protocol.md`, `Pebble.md`, `requirements/REQ-WATCH.md` and `REQ-ANDROID.md` (and `spec/400-ui/AndroidUI.md` / `WatchUI.md`, outside this scan). Protocol.md says "Minor versions only add optional keys and flag bits", so a new event in 1.3 needs that sentence widened; older peers already ignore unknown events (watch `default: break`, phone `decodeInbound` -> null). Pebble.md still says the watch should "Persist only minimal display state". Requirements to amend: REQ-WATCH-012/014/015/016/022/024 (all say "SHALL NOT change the protocol"; 024 adds "or the phone app"); REQ-WATCH-017 has the same words about its watchdog, which #102 does not touch. There is no REQ-PROTOCOL file; the next free IDs are REQ-WATCH-025 and REQ-ANDROID-021.
14. **Previews: what the capture tool lacks.** See [api-documentation.md](api-documentation.md) "Watch Preview Capture Surface": 10 accents missing, names unusable as resources (hyphens, size suffix), no output to `drawable-nodpi/`, no optimisation, and the committed `screenshots/` lack the v0.0.76 Shortcuts shots. Per platform the seven visual settings have 29 values (16 + 2 + 2 + 2 + 2 + 3 + 2), or 23 distinct images when the default shot stands for every default value; at the current 0.9-2.4 KB per PNG, three platforms cost roughly 125-160 KB. The ETA display value is called "Time to arrival" in the menu but "Time left" in the Shortcut notice and action name, so the phone strings must pick one.
15. **Where a completeness check is enforced.** `scripts/test-all.sh` runs spec integrity, protocol `--check`, version sync, the watch host tests, rules, route-capture tests and `gradlew test lint`, but CI does not run it (android.yml runs the Android tests and lint, watchapp.yml only builds). A preview check in `test-all.sh` is therefore local-only; a JVM unit test (resources are merged into unit tests) would run in CI, but cannot read `theme.h`, so the enum list would need a checked copy on the Kotlin side or a Python check that is also wired into CI. Release resource shrinking means drawables looked up by a built name are removed unless kept.
16. **Phone UI patterns to reuse.** Screens are stateless composables wired in `MainActivity.AppNavHost` (string routes such as `"navigation-apps"`), sub-screens use `Scaffold` + `TopAppBar` with a back icon labelled `cd_back`, strings are English-only resources with `cd_*` content descriptions (AGENTS rules 16-17), and the row helpers `Section`, `ToggleRow` (one `toggleable` TalkBack node, `Role.Switch`), `NavRow` and `InfoRow` are `private` to `DashboardScreen.kt`, so a Watch settings screen must copy or move them. Enum-to-drawable mapping follows `DisplayLabels.maneuverIcon`. Tests: plain JUnit 4 for pure `core/` helpers (`DistanceQuantizerTest`), Robolectric for SharedPreferences repositories (`WatchSettingsRepositoryTest`), `FakeWatchTransport` (records `sent`, `emitInbound`) for the controller and codec, and the `NavigationAppsScreenTest` Robolectric Compose pattern.
17. **aplite heap.** About 3.9 KB is free at load after v0.0.76 (intent brief), and `window_disappear` already drops the glyph cache and QR so the menus fit. Code and static data share that RAM, so the sync code costs heap one for one: a table-driven encoder/decoder (one entry per setting: key, count or validator, getter, setter) is likely well under 1 KB of code plus about 23 x 12 bytes of table, whereas 23 hand-written write/find/validate blocks could reach 2-3 KB (estimates, to measure with `heap_bytes_free()` on aplite). The pure revision compare is a few dozen bytes.

## Key implementation decisions

- **One table on the watch.** `settings_sync.c` holds range, capability, default and persist key for the 23 settings in protocol order; `theme.c` stores the values in one `uint8_t` array, so loading, validation, encoding and decoding are loops. `settings_store()` writes only a changed value; `settings_set()` is a watch edit and calls the edit handler (revision bump plus SETTINGS), so every edit path (menus, Shortcuts door, Touch, shortcut actions) is covered in one place. A phone edit uses `settings_store()` and never echoes.
- **Outbox.** READY and SETTINGS are pending bits; a message is built when it goes out, so it carries current values. One retry, then held until the phone reconnects.
- **Phone send policy.** "Open" means the watchapp sent its settings in this session and has not closed (companion `onAppClosed`) or failed a send. Edits go through `WatchTransport.sendToOpenApp`, which never relaunches; the phone sends only the edited settings, and keeps them pending until the watch's reply confirms them.
- **Merge rule on the phone.** The phone keeps its edits only when it has some and its revision is newer; the same revision and values confirm them; otherwise the watch wins and its values replace the queued ones (a 1.3 watch always sends all 23).
- **Previews** are captured by setting each value through a SETTINGS message (no emulator wipe), optimised to exact-palette PNGs by Pillow (the pebble tool's Python), and named by value (`watch_preview_accent_navy_basalt`).
- **aplite memory.** Measured with identical temporary logging: every Settings path is 16 bytes below v0.0.76 (top menu 1764 vs 1780, action list 424 vs 440), the clean build reports 3903 bytes free at load (v0.0.76: 3916). Savings that paid for the sync are listed in `docs/IMPLEMENTATION_STATUS.md`. The glyph-pack door, which faulted in the instrumented v0.0.76 baseline, now holds one preview glyph at a time.

## Traceability IDs

`traceability.json` uses FR1–FR9 as in `requirements.md`, and numbers its unnumbered non-functional requirements in their order there: NFR1 aplite memory, NFR2 reliability (outbox), NFR3 flash (changed values only), NFR4 testability (pure units), NFR5 compatibility (1.2 and 1.3 peers).

## Deviations from the plan

- **Settings menu refresh.** The plan said reload open menus and pop to the root only when row counts change. To stay within aplite's heap, a phone edit closes any open door back to the top menu and reloads it (FR3 allows "refreshes an open settings menu or closes it back to its root").
- **AppMessage buffers not resized.** On aplite `app_message_open` with the maxima takes no app heap (measured), so there was nothing to win; the heap budget was met by the code savings above.
- **Extra behaviour-neutral changes for aplite:** name tables, table-driven menu rows, arithmetic maneuver bitmap lookup with compile-time checks, per-draw glyph-pack previews.
- **Capability and platform encodings** are generated from new sections of `protocol/protocol-definition.json` (the plan only named the values).
- **Test runner.** `scripts/test-watchapp-unit.sh` gained `// Links:` so `test_settings_sync` can link `revision.c`.
- **Pure-part placement.** The capability bits for the build (`sync_build_caps`) are in the pure `settings_sync.c` via the SDK's compiler defines, as planned; the Pebble glue is its own file, `settings_sync_glue.c`, as the test instructions allowed.
